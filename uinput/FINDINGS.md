# Находки эксперимента uinput (2026-08-31, ThinkPad T14, Debian 13, ядро 7.0.13+deb13)

Код готов: устройство создаётся, события кодируются верно (тесты),
probe-команда печатает слово в фокус. Но на ЭТОЙ машине uinput
неработоспособен на уровне ядра:

- модуль загружен (lsmod, /proc/misc: «223 uinput»), secure boot off,
  контейнера нет;
- /dev/uinput открывается (после udev-правила deploy/60-lapsus-uinput.rules),
  но КАЖДЫЙ ioctl возвращает EINVAL — включая тривиальный UI_GET_VERSION,
  который в ядре обрабатывается безусловно (put_user версии);
- воспроизводится из Go, из Python (fcntl) и systemd-udev'ом
  (udevadm trigger --name-match=uinput → «Invalid argument»);
- обычные evdev-ioctl (EVIOCGNAME на event0) из тех же процессов работают.

Вывод: uinput-интерфейс ядра на этой сборке/состоянии сломан или
принудительно ограничен. Проверить: sudo dmesg | grep -iE 'uinput|lockdown',
перезагрузка (свежее состояние модуля), сравнение на стоковом ядре.
Код ветки готов к использованию, как только uinput заработает:
фильтр самоэха в демон уже включён (устройство «lapsus-virtual-keyboard»
игнорируется evdev-ридером).

До слияния в master: держим ветку, wtype остаётся основным инъектором.
